Backend architecture: feature modules, engines, and build setup. The conventions below apply to the file being read.

# Backend Architecture (`back`)

- **Entry point**: `src/index.ts` — imports feature modules and calls `boot()`.
- **Features**: `src/features/` — registered via `registerFeature()`. 
- **Engines**: `src/engines/` — infrastructure layer.
- **tRPC routers**: `src/features/app-router/<domain>/<domain>-router.ts` — each domain has a router file that wires tRPC procedures to service methods. Input validation uses Zod.
- **Query outputs must never resolve to `undefined`**: a `.query()` resolver returning `undefined` crashes TanStack Query on the client (`Query data cannot be undefined`). For absent/not-found results, declare the `.output()` schema as `.nullable()` (NOT `.optional()`) and coalesce the resolver result with `?? null` (e.g. `await services...getX(input.id) ?? null`). The domain layer may keep returning `undefined` for "not found" — only the tRPC boundary converts to `null`. Enforced by the `app/no-optional-query-output` lint rule. Mutations are exempt (`useMutation` tolerates `undefined`).
- **The tRPC procedures are a contract outside this repository**: XTM One calls OpenCRQ by procedure name. It pins procedure paths and types only; each instance hands over its own input schemas at runtime, in the XTM One registration (a fingerprint on every heartbeat, the manifest itself when XTM One asks for it) and through the authenticated `procedureManifest` query, both built from the router `/trpc` serves. `back/trpc-procedures.json` is that same manifest as a file for review: a back test fails while it is stale, and `yarn workspace @app/back trpc:manifest` regenerates it. A path that disappears from its diff, renamed or removed, breaks that integration until its pinned copy and its calls are updated, and so does an input that accepts less: a new required field, a narrowed enum, which XTM One's tools then refuse at call time on that instance. The manifest pins no output, but XTM One's OpenCRQ tools print fields of the responses (XTM One records those responses in its own tests): a field leaving an output schema is checked there as well as in the front, or a tool quietly prints `?` where the field was. What XTM One's tools send is held against the router here: `src/features/app-router/xtm-one-contract.test.ts` fails on a procedure a tool sends that is no longer served or that changes type from the one XTM One pinned, a field of a call its input no longer accepts, or a field a closed call never sends that the input now requires, naming the tool; it reads XTM One's `tool_procedures.json`, `tool_input_keys.json` and `opencrq_trpc_procedures.json` at the commit `src/features/xtm-one/contract/xtm-one-contract.json` pins, downloaded once per commit into `node_modules/.cache/xtm-one-contract/`. Renovate moves that pin to XTM One's latest `main` in a weekly pull request; a deliberate break moves it in the pull request that makes it with `yarn xtm-one-contract --ref <commit>`.
- **A field XTM One still sends is deprecated before it is removed**, when OpenCRQ merges ahead of the XTM One change that stops sending it. The input keeps the field, ignores it, and marks it with `.meta({ deprecated: true, description })`, which the manifest carries as a JSON Schema `deprecated`, the way OpenAEV marks an ignored input with `@Schema(deprecated = true)`; an enum member XTM One still sends is kept and ignored the same way. A call left with nothing but the deprecated field is still refused, never answered with a success that wrote nothing. A follow-up issue, blocked by that XTM One change, removes the field: its pull request stays red on the contract guard until Renovate's pull request pins an XTM One commit without the field on `main`, and a rebase on `main` then turns it green.
- **What Ask Ariane can do is written in XTM One, not here**: each of its OpenCRQ tools is a call, there, to a procedure this router serves. A new capability for it only asks this side to serve the procedure, or to widen its input, and to regenerate `back/trpc-procedures.json`; a procedure already served needs no change here. XTM One then pins the procedure and writes the tool, and Renovate's pull request pins that XTM One commit here: `src/features/xtm-one/contract/xtm-one-contract.json` is never edited by hand. The contract checks which procedures and fields a tool sends, not the values: a value its input stops accepting surfaces only when the tool is called on that instance.
- **A refusal a client must tell apart carries a `reason`**: a tRPC code such as `CONFLICT` is shared by several domain errors, and the message is prose. A `StructuredError` a client switches on overrides `reason` with a stable code (`STALE_WRITE`, `ASSESSMENT_PUBLISHED`), and the error formatter sends it as `data.reason` (`null` otherwise) when the error reaches it as the `TRPCError` cause, which `withConflictOn` and its siblings pass. A code is part of the contract above, frontend and XTM One alike: never rename one, and never match on a message.
- **Service instantiation**: `app-router-router.ts` calls `instantiateServices(db)`, then `createTenantProcedure(services)`, whose return type is the `TenantProcedure` a tenant domain router takes as its parameter. A router reserved to security managers takes `TenantSecurityProcedure` instead (`createTenantSecurityProcedure`, which refuses a caller without `MANAGE_SECURITY`). (`createServices()` is the lower-level form the job runtime uses with an explicit service list.)
- **A value computed from other tables is written by an observed recompute job**, never inline in a service or in the transaction that changed its inputs: the job's read set is what makes it re-run when a source table or a setting changes, so a hand-written recompute path is a second trigger that forgets. A value that also depends on the clock declares `daily: true` and accepts a day of staleness; a job that would rewrite every row on every run scopes itself with a watermark (a `*_computed_at` column against the source rows' `updated_at`).
- **The values kept by a trigger instead are a finding's current state** (`asset_evidence.current_state`, `current_state_changed_at`, `current_state_since`) **and its latest test verdict** (`latest_verdict_exposed`, `latest_verdict_observed_at`). A list ordered or filtered on the state must see a dismissal in the transaction that wrote it, which a recompute job cannot: the job leaves the list a run behind. The verdict is the latest row of a log that several readers derived on every call, and a job would leave the control pages a run behind the sync that logged it. `asset_evidence_history_refresh_state_inserted` and `_deleted` re-derive the columns from the whole history of the findings a statement touched (`asset_evidence_history_refresh_state`), so a batch, a backdated row and a deletion reach the answer a plain append does. The derivation is written once, as the pure `IMMUTABLE` functions `asset_evidence_derived_state` and `asset_evidence_history_entered_at`, which the trigger, the integration tests' whole-table re-derivation and `historyRowEnteredAt` all call: a function in a migration reads no table, or it hides reads from the procedure observation. `asset_evidence_verdicts_refresh_latest` re-reads the latest verdict of the findings an insert into `asset_evidence_verdicts` touched; a verdict is deleted only with its finding. Both lock the touched findings (`FOR NO KEY UPDATE`, in id order) in a statement of their own before deriving: a statement that waits for a row lock does not re-read the log, so overlapping writers would otherwise each derive from a log missing the other's row. A transaction writing several findings has already locked them, in the one order `compareFindingKeys` (`supporting-assets/finding-lock-order.ts`) defines: a sync's upsert sorts its batch by it, and the retirement pass (`recomputeEvidenceStateForAssets`) takes `lockFindingsOnAssets` before it reads their sources, in a transaction that holds no other finding, which `claimFindingLocks` enforces: a step refuses to run once the transaction holds a table lock on `asset_evidence` above a read's, left by any earlier lock or write of a finding. Two orders would deadlock. A writer inserts the history or verdict row and nothing else; a reader reads the column. A reading of a past instant (`upTo`, the proven-posture replay) has no stored answer and reads the log. A bulk write that disables user triggers (the large-estate seed) writes the five columns with the row. A new value does not follow this: it earns a trigger only by being ordered or filtered on by a list that cannot trail a write.
- **An observed job subscribes to every table it reads**: the recompute dispatcher re-enqueues a job kind whenever a table its last successful run read is written, so a read for nothing buys a full recompute on every change of that table, and a read of a global table buys one per tenant. Split a query shared with a read surface rather than narrowing the observation, and build such a run's services on `ctx.runDb`, never on the shared instance, which would run unobserved. A run that resumes from a state (a continuation's, or a snapshot a retry picks up) adds its tables to the persisted set instead of replacing it, since it read only what was left of the pass: a pass split across continuations stays subscribed to everything it reads, and the next run that starts afresh narrows the set again. A projection the job only rewrites is upserted with `onConflictDoOverwrite`, which the writer certifies so the target stays out of the read set; the same upsert spelled as `onConflictDoUpdate` with `excluded.*` plans exactly like a read-modify-write and subscribes the job to its own output. Two jobs whose writes wake each other are reported by the dispatcher, not refused: the watermark is what makes such a loop converge, since the job a peer's write wakes finds nothing stale and writes nothing. A cycle that does not converge shows as a (kind, tenant) other observed jobs alone keep asking for, which the dispatcher logs by name (a connector sync or any job no change wakes is an outside ask, like a user's), and the fix is the missing watermark, never the routing. One writer is never routed, the `jobs-retention` purge (`UNROUTED_ORIGINS`): it deletes only rows past every reader's window, so its deletes wake no recompute. The enqueue is throttled, not debounced: the first event of a burst books the run `clamp(factor x last run duration, floor, cap)` later and every event until then folds into it, so a table written faster than that delay drives the job at that cadence instead of starving it, which is what a debounce that re-arms on each event does under a backfill.
- **Every keyed enqueue is a promise, not a throttle.** `enqueueJob` folds an ask into the active run holding its key rather than starting a second one, and the run it folds into answers that ask only if it starts clean: one already running, or one queued to resume from a `state_snapshot`, read their inputs before the ask existed. The queue therefore marks such a run `absorbed_ask` and books exactly one more run of the key when the execution ends, whatever it ended as, so a new enqueue site inherits a full extra run per ask absorbed mid-flight, unless it passes `skipIfActive`, for an ask any run under way already answers (a scheduled occurrence). A `saveStateSnapshot` carries that second meaning: a checkpoint makes the attempt that follows a resume, so it no longer answers what the run absorbed. A run sent back to `queued` without one does answer it, and takes over its `interactive` window when somebody waits on it. The booking happens where the key is known free, which for a run interrupted mid-handler is the runtime, not the transition: a cancel or a runtime-limit abort makes the row terminal while the handler still writes. The row keeps the payload it was booked with, unless its kind declares a payload fold in `module/src/modules/jobs/payload-folds.ts` (a `crq-simulation` profile says what a run computes): the fold then merges the ask's payload into the held one under the row's lock, at enqueue and when a successor finds its key taken, and the merged payload is what the row's retries and the run booked after it read. A fold, a `skipIfActive` ask, or a scheduled connector occurrence skipped for an active run (`askActiveRuns`) from an asker other than the row's `triggered_by` marks it `asked_by_others`, which a continuation keeps and a retry from the DLQ clears.
- **A handler whose inputs are on their way defers its run, it does not fail it.** It throws `InputsNotReadyError`, and the runtime puts the run back in `queued` with no `job_errors` row and no `error_message`, the attempt handed back and an absorbed ask cleared as a retry clears it, then arms a drain timer, since a future `run_after` is otherwise only picked up by the polling fallback. As on every return to `queued` (a retry, a shutdown release, an orphan requeue), a run asked to stop is cancelled there instead, since requeuing it would clear the request before the runtime's poll reads it. The run waits a quarter of its age, between 2 and 30 s, so a long wait costs a few dozen claims. Past `maxWaitMs`, counted from its first start so that a wait in the queue is not counted, it fails as the `NonRetryableError` it extends, which is also how every caller other than the runtime reads it. `deferralPolicyFor` derives `maxWaitMs` from `recompute.debounce_cap_ms`, since the job a deferred run waits for is one the dispatcher books.
- **Every tRPC query procedure is observed too**: the events feature attributes each statement of a query call to its procedure (through the Drizzle logger of the shared instance and an async scope opened by the tRPC middleware) and EXPLAINs each distinct statement shape once with `GENERIC_PLAN` (PostgreSQL 16 or later), so a `data_changed` doorbell can name the procedures a written table made stale. The plan is the ground truth, so a read hidden in a SQL function body is not seen: a query procedure must not depend on one. A statement Postgres refuses to plan generically widens the procedure to every doorbell, and so does a read of a table without a `notify_data_changed` trigger; a procedure that attributes no read at all is named too, since its result may come from what the tRPC context resolved. Such a procedure declares the tables its result depends on in its meta instead (`.meta({ reads: [schema.users] })`, `[]` for a result held in process memory), added to what the call is still observed reading, so it names only the tables no statement of the call reads. A read that fills a process cache shared across calls runs inside `outsideObservedCall`, so it is nobody's: attributed to the call that missed the cache, it would subscribe that one procedure, and no other, to its table. The reader scope does this with the tenant's threat visibility, kept with the scope and cleared by `opencti.setThreatVisibility`, since the table holding it is rewritten by every batch of the OpenCTI stream. A DELETE is a change of every table whose doorbell finds its tenant through the deleted row, and that closure (`createDoorbellTopology` in `module`) is the one the recompute dispatcher routes on too. The index lives in one process: with several http replicas, a client's SSE stream and its queries must reach the same one.
- **A job kind is declared twice, on purpose**: registered with its handler in its feature, and entered with the same `observed` / `daily` / `serialized` / `serializedWith` flags in `JOB_CATALOGUE` (`module/src/modules/jobs/catalogue.ts`). `serializedWith` puts two kinds in one per-tenant slot, so a run of either waits while the other runs: the price job and `crq-simulation` share one, since pricing is one queue per tenant. The handler registry only fills in the worker process, so the `jobs` router, which runs in the http process, reads the catalogue instead; `job-catalogue-registry-agreement.test.ts` fails when the two disagree. A run's `payload` is the one handler-defined field that reaches the browser: it leaves only through `serialisePayload` (secrets redacted, capped at `PAYLOAD_CHAR_CAP`), on `JobRunListItemSchema` and the run detail, from procedures behind `requirePayloadAccess`, the gate `jobs.listLogs` and `jobs.listRunLogs` sit behind too for the third-party messages a log line carries, and `jobs.listJobErrors` for any run no connector owns, since the connectors' Works tab reads a connector run's errors under its own gate. A run search never matches the payload: the response redacts it, and a match on the raw text would give a redacted value away one character at a time. `RunListItemSchema` stays payload-free because `connectors.listRuns` shares it under another capability. `jobs.cancelJob` and `jobs.retryFromDlq` take the same access, except on a run the caller started, and a cancel of it only while no other asker folded into it (`asked_by_others`). Such a cancel drops the asks the run absorbed, all of them the caller's, rather than booking a `system` run to answer them.
- **Build**: esbuild with custom plugins (not Vite). Dev mode: `tsx esbuild.ts --start --watch --development`.
