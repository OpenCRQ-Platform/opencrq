# Internationalisation (i18n)

The frontend uses **Lingui v5** for translations. Locales: `en` (source), `fr`.

## Locale persistence

The language shown resolves in this order (`resolveLocale`, `lib/locale-utils.ts`): the user's own language, the tenant's default language, the browser's language when it is a supported locale, then English. A setting left to Automatic is null and defers to the next step.

- **`users.locale` and `tenants.default_locale` (tRPC)**: the two settings, null for Automatic. A user sets the first on the profile page, a tenant administrator (`MANAGE_SECURITY`) the second on Settings > Parameters.
- **`userPreferenceCollection` (`@tanstack/react-db`)**: local reactive cache backed by `localStorage` (`app:user-preference`). It holds the **resolved** locale, never a setting, and the bootstrap reads it before the first network call.

### Data flow

| Scenario | Source | Behaviour |
|---|---|---|
| Bootstrap (`main.tsx`) | `userPreferenceCollection`, else the browser | `loadCatalog(locale)` runs before `root.render()` |
| First answer after boot | `getUserLocale`, and `tenants.getTenant` for the tenant on screen | `LocaleSyncProvider` resolves (`syncedLocale`) and, on a mismatch, calls `loadCatalog()` |
| Tenant switch | Same | `LocaleSyncProvider` caches the new resolution (`rememberLocale`) and reloads the page |
| A setting changed by someone else (another member's tenant default, the user's own language set in another tab) | Doorbell | `LocaleSyncProvider` only caches the new resolution: the next load shows it, and nothing in progress is lost (`localeSyncStep`) |
| Language change (profile) | User action | `updateUser({ locale })`, `null` for Automatic, then the profile caches the new resolution and reloads |
| Tenant default change (Settings > Parameters) | User action | `setTenantDefaultLocale`, then the field caches the new resolution and reloads only when the administrator's own language changes |
| Pages outside a tenant | User setting only | A user on Automatic keeps the locale shown |

## Translation API — `t` by default, `i18n._` for descriptor-based strings

**Never use `useLingui()`**. The app does not support live locale switching (a full page reload is required). Use the static macro instead:

```ts
import { t } from '@lingui/core/macro';          // translated string
import { msg } from '@lingui/core/macro';         // MessageDescriptor (for meta, lazy eval)
import { Trans } from '@lingui/react/macro';      // JSX with dynamic interpolation
import { i18n } from '@lingui/core';              // global instance, only for i18n._(descriptor)
```

| Use case | Correct |
|---|---|
| String in JSX / prop | `t`My string`` |
| Dynamic string prop in React Compiler-sensitive paths (e.g. drawer `title`) | `i18n._({ id, message, values })` (single descriptor object) |
| JSX with dynamic value | `<Trans>Hello {name}</Trans>` |
| Lazy string (e.g. mutation meta) | `msg`Success`` + consumed by `i18n._()` |
| Translating a descriptor | `import { i18n } from '@lingui/core'; i18n._(descriptor)` |

## Rules

- **No `useLingui()` hook** — `t` is a static import, not reactive.
- **Prefer `t` for most strings**, but use `i18n._({ id, message, values })` for dynamic string props where tagged template interpolation can fail under React Compiler `all_errors`.
- **Avoid interpolated tagged templates** (`t`... ${value}`` and `msg`... ${value}``) in compiler-sensitive component code paths.
- **No object properties in `<Trans>` or `t`...``** — extract to a local variable first: `const { id } = obj; <Trans>ID: {id}</Trans>`.
- **`t` is stable** — if a justified `useMemo`/`useCallback` remains, don't add `t` to deps.
- **Dynamic translated lists** (e.g. locale labels) must be functions, not module-level constants, so they are evaluated after locale activation: `export const getSupportedLocales = () => [{ value: 'en', label: t`English` }]`.
- **Dates and numbers follow the application language, never the browser's.** Use `formatDate`, `formatDateTime` (`utils/date-utils`) and `formatNumber`, `formatFixed`, `formatAtMost`, `formatFractionAsPercent` (`utils/format-number`), `formatList`, `formatDateWith`, `formatDollar`, `formatCompactCount` and `formatBytes`, since `toFixed` always writes a `.`, or pass `i18n.locale || 'en'` to `toLocale*String` and `Intl.*Format`. With no locale the runtime falls back to the browser's language, and one screen then mixes two. `no-restricted-syntax` flags a call with no locale in `front` and `utils`, a bare `i18n.locale` (empty until a catalogue is active, when the formatter throws), `toFixed`, and `navigator.language(s)` handed to a formatter, which is the browser's choice spelled out; reading it to pick a default stays legal (`eslint-rules/src/rules/locale-formatting.ts`). A formatter given a fixed locale (`'en-US'`) ignores the application language too, so keep one only where the text is parsed, never shown.
- **A percentage is printed from the figure the code holds.** A fraction goes to `formatFractionAsPercent`, which scales it in decimal, never multiplied by 100 first: `0.145 * 100` is 14.499999999999998 and prints 14% where 15% is right. `formatPointsAsPercent` takes a figure already in percentage points, which code holding a fraction gets with `toPercentPoints`, and a percentage compared or subtracted before it is printed is rounded with `roundPercentPoints` (both `@app/utils/decimals`, scaling in decimal as the percent style does), so either agrees with the one on screen.
- **Never special-case a language.** The catalogue holds two today and others can follow: separators, the first day of the week and the percent sign come from the runtime (`Intl`, `formatToParts`, `firstDayOfWeek` in `utils/date-utils`), never from a table of languages. Languages that write digits of their own are not handled by the amount input, since none is in the catalogue.
- **No HTML entities inside `<Trans>`** — use the literal character directly: `<Trans>We're sorry</Trans>`, not `<Trans>We&apos;re sorry</Trans>`. Lingui resolves entities during extraction so the msgid is identical, but the source is harder to read with entities.
- **Keep formatting inside `<Trans>` — never split a sentence** — when formatting (bold, links, custom components) appears within a sentence, keep the whole sentence in **one** `<Trans>` with the element inside. Splitting a sentence across multiple `<Trans>` fragments destroys the translation context: the translator sees disconnected fragments and cannot reorder words, which is required in many languages. Variables (`{count}`, `{name}`, …) and JSX/HTML elements are all allowed inside `<Trans>`.
  - ✅ `<Trans>You have {count} unread messages.</Trans>` — variable inside `<Trans>` is fine
  - ✅ `<Trans>Click <strong>Save</strong> to confirm your changes.</Trans>` — formatted element inside keeps the full sentence together for the translator
  - ✅ `<Trans>Are you sure you want to delete <strong>{name}</strong>?</Trans>` — full sentence with both a formatted element and a variable
  - ❌ `<Trans>Click </Trans><strong>Save</strong><Trans> to confirm your changes.</Trans>` — splitting breaks the sentence; the translator cannot reorder words
  - ❌ `<Trans>Are you sure you want to delete </Trans><strong>{name}</strong><Trans>?</Trans>` — same problem
  - ❌ `<p>Total: <Trans>{count} items</Trans></p>` — plain text outside any `<Trans>`
- **No string concatenation for i18n** — never build a translatable sentence by concatenating `t` fragments, template literals, or mixing raw strings with `<Trans>`. The whole sentence must be **one translatable unit**. Concatenation breaks extraction and makes translation impossible.
  - ✅ `` t`Created ${count} items successfully.` ``
  - ❌ `` t`Created` + ` ${count} ` + t`items successfully.` ``
  - ❌ `` `${t`Created`} ${count} ${t`items`}` ``

## French glossary

The French catalogue speaks to CISOs and their teams, so every product concept has **one** French
term, the one those readers use. A new `msgstr` naming a concept below takes that term, and a term
missing here is added to the table before it is used. Three rules pick a term:

- **The field's word over the dictionary's.** French security teams work with English-language
  tools and keep some words as they are: finding, tenant, backlog, TTP.
- **A French standard over a literal translation**, when one exists: ISO 27005, EBIOS RM and the
  business continuity vocabulary (DMIA).
- **One word, one concept.** A French word the catalogue already gives a concept is never reused
  for another one, which is why "facteur", "déclaration", "preuve" and "impact" each appear once.

catalogue (`opencti-platform/opencti-front/lang/front/fr.json`), so an entity carries the same name
here and in the platform it was ingested from. The authority inside that file is the
`entity_<Type>` keys: its prose keys have drifted and hold several spellings of the same type.

| English | French | Never |

| Malware | code malveillant | logiciel malveillant, maliciel, malware |

| Campaign | campagne | |
| Tool | outil | |

A MITRE ATT&CK **technique** stays "technique" in both languages. It is the ATT&CK concept, not the
STIX `Attack-Pattern` entity, so only a string whose English reads "attack pattern" becomes "motif
d'attaque".

Two French words already carry an unrelated meaning in this catalogue, and a new translation must
not take them back: "détection" is the control response and the detection accumulator, and
"observation" is a connector's first and last observed window. Neither is a STIX `Sighting`.

## ESLint rules (all `error`)

Defined in `eslint-rules/src/rules/lingui.ts`, applied via `linguiRules` in `front/local.eslint.config.ts`. Test files (`*.test.*`) are exempt from `no-unlocalized-strings`.

## Build setup

The Lingui macros (`t`, `msg`, `Trans`) require two Vite plugins configured in `front/vite.config.ts`:
- `@lingui/vite-plugin` — handles `.po` file imports at build time.
- `@lingui/babel-plugin-lingui-macro` — transforms macros via the `viteReact` babel config.

TypeScript support for `.po` imports is provided by `src/lib/lingui-po-module.ts` (uses `declare module '*.po'` in a `.ts` file to comply with the no-`.d.ts` convention).

## Catalog files

`.po` files live in `front/src/locales/{locale}/messages.po`. They are committed to git.

**Source file origins are disabled** (`origins: false` in `lingui.config.ts`). The `.po` files do not contain `#: file:line` reference comments. This avoids constant merge conflicts during rebases when files are moved or lines shift.

**After adding, modifying or removing `t`/`Trans`/`msg` calls**, always run these steps before committing:
1. `cd front && yarn i18n:extract` — updates `.po` files with new `msgid` entries
2. Translate the new entries in `src/locales/fr/messages.po`
3. `yarn i18n:compile` — verify compilation passes

**If the change deleted or moved any file carrying a string**, run `yarn i18n:extract:clean` instead of step 1. A plain extract only adds; it never prunes, so the msgids of a deleted component stay in the catalogues as obsolete entries. Everything then passes locally and the CI job below fails, since it extracts with `--clean` and compares.

## CI check (`ci-test-app.yml` → job `i18n`)

Runs `yarn workspace @app/front i18n:check` (`tsx scripts/i18n-check.ts`):

1. Snapshots all `.po` file contents in memory.
2. `lingui extract --clean` — adds any new `msgid` with empty `msgstr ""` and removes obsolete entries.
3. Compares `.po` files against the snapshot — fails if any file was modified by step 2, meaning the developer forgot to run `i18n:extract` before committing.
4. `lingui compile --strict` — fails if any `msgstr ""` is empty in a non-source locale.
